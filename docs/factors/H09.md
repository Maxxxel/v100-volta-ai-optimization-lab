## Theory and Volta implications

CUDA MPS changes multi-process resource sharing. It is outside a one-heavy-job research protocol unless separately admitted.

On SM70, require an actually dispatched compatible kernel and include conversion, workspace, launch and verification costs. The 16 GB budget includes weights, attention KV, recurrent states, graph pools and transient allocations. Quality, end-to-end latency and energy per successful task take precedence over a token-throughput screen.

## Decision and remaining research

No MPS server/control process is running. Current valid profile has one model, one slot and no parallel GPU-heavy job. Starting a new sharing daemon without a compatible concurrency question does not test a useful MPS gain; it also changes process-ownership/telemetry boundaries. E09 slot-isolation issue remains unresolved.

**Remaining scope:** A justified compatible concurrency workload, proven state isolation, private MPS endpoints and lease/nonce/NVML attribution plus cleanup that retain existing single-job safeguards; no daemon started merely to increase coverage.

**Reopening condition:** A justified compatible concurrency workload, proven state isolation, private MPS endpoints and lease/nonce/NVML attribution plus cleanup that retain existing single-job safeguards; no daemon started merely to increase coverage.

**Next action:** State-safe isolated concurrency workload and separately admitted MPS lifecycle; no daemon installation now.

These canonical rationale excerpts preserve the original language. Potential combinations require independently qualified constituents and fresh interaction controls. Transfer to another model requires compatible architecture, weights, tokenizer, state layout and engine dispatch.
